# Codex 0.166 control channels: approvals, turns, joining, proxy, hooks, transcript, pane input

Research question: for Codex running in the shared app-server daemon (and with
`--no-daemon`), which channel should tmag use for `send`, `interrupt`,
`answer <request>` and `transcript_path`: the app-server JSON-RPC protocol,
reached by a short-lived client, or keys typed into the tmux pane?

Sources: `openai/codex` at tag `rust-v0.166.0` (commit `6ff1e1ca3b30`). Paths
are relative to `codex-rs/` and line numbers are at that tag. Protocol
stability was checked against schemas generated by the installed CLI
(`codex app-server generate-json-schema [--experimental]`). The installed CLI is
`codex-cli 0.166.0`. "The prior doc" is `docs/research/codex-pane-identity.md`
on branch `docs/v0.1-feasibility`, which covers how Codex picks daemon or
embedded mode and what a passive protocol observer costs.

Live observations were made on 2026-11-03 against a private app-server
(`codex app-server --listen unix:///tmp/tmag-research/codex.sock`), never the
user's shared daemon. TUIs ran in a private tmux server (`tmux -L research`,
private `TMUX_TMPDIR`) as `codex --remote unix://…` (daemon-style) and
`codex --no-daemon` (embedded). The test client was a ~150-line stdlib Python
WebSocket JSON-RPC client. The model was `gpt-6-luna` with low effort, under
approval policy `on-request` and sandbox `read-only`, with about 12 short turns
in total.

"Verified" means observed live or read directly in source. "Inferred" means
reasoned from code that was read, but not exercised.

## Live setup

  - A custom socket path is also symlinked into `/tmp/codex-daemon-<euid>/<sha256>`
    under its own hash, so it never collides with the default daemon's
    `ccc3ad55…`.

  - For C5, probe hooks were defined in the same session-flag table and trusted

    This needs no `config.toml` edit and no project trust.
- **TUIs:**
  - `codex --remote unix:///tmp/tmag-research/codex.sock -m gpt-6-luna -c
    model_reasoning_effort=low -a on-request -s read-only` (the remote TUI
    showed no folder-trust prompt).
  - `codex --no-daemon …` with the same `-c` tables. It showed a
    folder-trust prompt; "Open restricted" "will not change saved trust".
- **Client:** a WebSocket client connecting directly to the socket, or through
  `codex app-server proxy --sock …`.
  - A long-lived "client B" read commands from a FIFO and logged every message
    it received.
  - One-shot calls connected, sent `initialize` and one request, then
    disconnected.
- **Approval policy:** `-a` accepts only `on-request` and `never`, and

  commands fail at once, so long-running commands had to be escalated.

## C1. Approvals and questions with several clients

### Who receives a server request

- Server requests are built per thread event with a snapshot of the thread's
  current subscribers (`thread_lifecycle.rs:562-570`) and sent to each of them
  (`outgoing_message.rs:180-191,436-462`).
- All of these use that one path (`bespoke_event_handling.rs`):
  - `item/fileChange/requestApproval` (656)
  - `item/commandExecution/requestApproval` (800)
  - `item/tool/requestUserInput` (854)
  - `mcpServer/elicitation/request` (920)
  - `item/permissions/requestApproval` (960)
  - `item/tool/call` (1111)
- The only exception is user-verification elicitations, which are pinned to
  one owner connection (`outgoing_message.rs:390-408,593-605`).
- **Verified:** the TUI and client B (joined with `thread/resume`) both got
  `item/commandExecution/requestApproval` id 0 for a turn B had started. The
  TUI showed the normal dialog.
- A client that joins later gets every pending request of the thread right
  after its resume response (`thread_lifecycle.rs:1258`;
  `outgoing_message.rs:478-497`).
  - **Verified:** a client that connected while request id 2 was pending
    received it immediately after `thread/resume`. The resume response showed
    `status: {type: active, activeFlags: ["waitingOnApproval"]}`.
- **Inferred:** a thread with no subscriber still registers the request,
  because sending to an empty subscriber list succeeds. The request waits, the
  thread does not unload while the agent runs (`thread_lifecycle.rs:613-616`),
  and the next joiner receives it by replay.

### Who can answer

- A response is matched by request id alone. Any connection may answer; the
  owner check applies only to user verification (`outgoing_message.rs:593-612`).
- The first response removes the callback (`notify_client_response`,
  `:499-527`). The server then sends `serverRequest/resolved {threadId,
  requestId}` to all current subscribers (`thread_lifecycle.rs:1314-1336`,
  triggered from `bespoke_event_handling.rs:1675-1684,1983,2025`).
- **Verified, B answers:** B answered `{"decision":"accept"}`. The command ran,
  all subscribers got `serverRequest/resolved`, and the TUI dialog disappeared,
  replaced by "Ran touch a.txt". The TUI handler removes the visible or delayed
  prompt and writes no transcript entry (`tui/src/app/app_server_events.rs:309-338`).
- **Verified, both answer:** the TUI pressed `y` and B sent `decline` 0.5 s
  later.
  - The TUI's approval won: "✔ You approved codex to run touch b.txt", and the
    file was created.
  - B's late answer was dropped with `WARN codex_app_server::outgoing_message:
    could not find callback for Integer(1)`.
  - B received no error, because client responses get no acknowledgement in
    JSON-RPC.
- **Verified, another client declines:** a late joiner declined request id 2.
  The file was not created, but **the TUI then showed "• Ran touch c.txt └ (no
  output)"**. A decision made elsewhere is not marked as declined in the TUI.
- **Verified, interrupt with a request pending:** `turn/interrupt` resolved the
  pending request. Subscribers got `serverRequest/resolved` (id 3) and the TUI
  dismissed its dialog. Turn transitions cancel a thread's pending requests
  (`outgoing_message.rs:229-244`).

### A client disconnects while a request is pending

- Connection close removes the connection from every thread
  (`thread_state.rs:721-746`; `thread_processor.rs:3881-3897`). It cancels no
  server request; the callbacks are keyed by request id, not by connection.
- **Verified:** B disconnected while request id 2 was pending. The TUI dialog
  stayed, and a client that joined later received and answered the request.

### What this means for `tmag answer`

- The protocol channel works: join with `thread/resume`, take the replayed
  request, answer it, and disconnect.
- There is no "already answered" error. To know whether an answer landed, wait
  for `serverRequest/resolved` before disconnecting, and compare it with the
  item or turn outcome.
- Request ids are small per-server integers (0, 1, 2…), so they are not stable
  across daemon restarts. tmag should name a request by
  `(thread, turnId, itemId)`, which the request params carry.

## C2. Turns started, steered and interrupted by a second client

### Rendering

- **Verified:** B ran `turn/start` without subscribing. The TUI showed the
  user message, then "• Working (1s • esc to interrupt)", then the answer.
- The TUI draws another client's user message on `item/completed`
  (`tui/src/chatwidget/protocol.rs:581-583,690-694`), and sets running state
  on `turn/started` (`:89-117`).

### Interrupt

- **Verified:** `turn/interrupt {threadId, turnId}` from B, with an approval
  pending.
  - Order: response `{}` → `thread/status/changed idle` → `turn/completed`
    (`status: interrupted`) → `serverRequest/resolved`.
  - The TUI printed "■ Conversation interrupted - use /feedback if something
    went wrong".
- The response is deferred until `TurnAborted`
  (`turn_processor.rs:1424-1462`).
- Error cases:
  - Wrong turn id: "expected active turn id X but found Y".
  - Idle: "no active turn to interrupt".
- **Anomaly (verified):**
  - The setup: a turn was steered by a second `turn/start`, then interrupted.
  - After that, the app-server's in-memory tracker (`thread_state.rs:210-212`)
    still reported the interrupted turn as active.
  - A second `turn/interrupt` for that turn id **never got a response** (more
    than 5 s, and none by the end of the session).
  - An interrupt with another id was rejected with "expected active turn id
    \<interrupted turn\> but found …", even though `thread/read` said `idle`
    and `thread/turns/list` said `interrupted`.
  - Every interrupt call therefore needs a client-side timeout, and a turn
    already known to be ended should not be interrupted.
  - That the cause is the steer is inferred.

### Steer and turn/start on a busy thread

- `turn/start` calls `start_or_steer_turn` (`turn_processor.rs:640`). On an
  active turn it **steers**: the response carries the active turn's id, and
  the turn is not rejected or queued (`core/src/codex_thread.rs:463-475`;
  protocol doc "Ignored when this request steers an already-active turn",
  `v2/turn.rs:182-183`).
- **Verified:** a `turn/start` sent while turn `…ca8c…` waited on approval
  returned `turn.id = …ca8c…`.
- There is no public "start only if idle" mode. `start_turn_if_idle` is used
  only by `thread/sample` (`app-server/src/thread_sample.rs:271`).
- **Consequence:** tmag cannot rely on the server to refuse a busy thread. Its
  own idle gate stays necessary. A race between that gate and a TUI user means
  tmag's prompt is silently merged into the user's turn. A mismatch between the
  returned id and tmag's expectation can be detected, but not prevented.
- `turn/steer` preconditions (`turn_processor.rs:1026-1169`):
  - non-empty `expectedTurnId`, equal to the active turn's id;
  - the active turn is a regular turn (review and compact turns cannot be
    steered);
  - the output schema matches;
  - the input is non-empty.
  - **Verified:** "expected active turn id \`wrong-id\` but found \`…\`" and,
    when idle, "no active turn to steer".
- `turn/start` and `turn/steer` both overwrite the thread's
  `app_server_client_name` (`turn_processor.rs:1007-1024`). It is last writer
  wins, and is the legacy `notify` `client` field.

## C3. Joining a loaded thread and reading without joining

### Joining

- `thread/resume` on a loaded thread runs `resume_running_thread`
  (`thread_processor.rs:4628-4830`): it adds the caller as a subscriber
  (`thread_lifecycle.rs:1156`) and returns the live thread. It does not reload
  or fork.
- With `excludeTurns: true` the response holds no history.
- **Verified:** the response came in ~9 ms, followed by `thread/goal/cleared`
  and any pending requests.

Side effects of joining:

1. **Overrides.** Overrides in the resume params (model, cwd, approval policy
   and so on) are ignored with a WARN while another client is subscribed. If
   the thread is idle and has no subscribers, it is **shut down and
   cold-resumed** instead (`:4697-4750`), which reruns SessionStart (`resume`).
   So send no overrides.
2. **Client name.** It overwrites the thread's client name (`:4815`).
3. **Idle hooks.** It calls `emit_thread_idle_lifecycle_if_idle` after the
   response (`thread_lifecycle.rs:1263`), which re-runs extension `on_thread_idle`
   contributors (`core/src/tasks/lifecycle.rs:63-88`). Whether, for example,
   the goals extension then acts on a thread with an active goal is inferred,
   not observed.
4. **Unload timing.** The thread stays loaded while any subscriber is
   connected. It unloads `thread_unload_delay` (60 s) after the last subscriber
   leaves *and* the thread went inactive (`thread_lifecycle.rs:56-63`).
   - **Verified:** the TUI quit while another client stayed subscribed; the
     thread was still loaded at +75 s.
   - **Verified:** the last client sent `thread/unsubscribe` and the thread
     unloaded exactly 60 s later. `thread/closed` was broadcast to all
     connections.
   - A one-shot client that disconnects within milliseconds does not change
     the timing. A held connection delays SessionEnd.
5. **Originator.** `initialize` with a non-internal `clientInfo.name` sets the
   process-global originator, first caller wins
   (`initialize_processor.rs:127-191`; internal names at `:19`).
   - **Verified:** my first one-shot client reached a fresh server before the
     TUI did. Every thread created afterwards recorded `originator:
     "tmag-research"` and `source: "vscode"`.
   - In a fresh daemon a tmag client could therefore become the originator for
     all threads, which also affects the request User-Agent. The prior research
     doc lists the analytics side effects.

Other joining behaviour:

- **A loaded thread before its first turn cannot be joined.** `thread/resume`
  fails with "no rollout found for thread id …" (verified), because no rollout
  exists until the first turn.
- `turn/start` does **not** subscribe the caller (verified). Only
  `thread/start`, `thread/resume`, `thread/fork` and the realtime path attach
  listeners.

### Broadcasts every connection gets, joined or not

- `thread/started`, `thread/status/changed` (`active` with `activeFlags`
  `waitingOnApproval` or `waitingOnUserInput`, `idle`, `notLoaded`),
  `thread/name/updated` and `thread/closed`.
- That makes a passive observer possible. The prior doc covers its analytics
  cost.
- **Verified:** helper threads appear too: an ephemeral title generator with
  `threadSource: "thread_title"` and `path: null`. tmag would have to filter
  them.

### Reading without joining

- `thread/read`, `thread/turns/list` and `thread/items/list` read the thread
  store and need no subscription (`thread_processor.rs:3069-3140,3324-3410,3685-3753`).
- `thread/read` and `thread/turns/list` merge the live active turn for a loaded
  thread (`:3380-3391`).
- **Verified on an unloaded thread:** all three returned data (`status:
  notLoaded`, 4 turns). `thread/loaded/list` afterwards did not include the
  thread, and no SessionStart hook fired.
- `thread/items/list` returned items with `turnId` on a `paginated`
  history-mode thread. 0.166 creates new threads as `historyMode:
  "paginated"`.
- `thread/unsubscribe` returns `unsubscribed`, `notSubscribed` or `notLoaded`
  (`:1126-1156`).

## C4. `codex app-server proxy`

- **Usage:** `codex app-server proxy [--sock PATH]` (`cli/src/main.rs:640-641,706-710`).
  - Without `--sock` it connects to `$CODEX_HOME/app-server-control/app-server-control.sock`
    (`:1474-1483`), which is a symlink to `/tmp/codex-daemon-<euid>/<sha256>`.
  - It accepts `-c/--enable/--disable` but rejects `--strict-config` and
    remote flags.
- **Framing:**
  - The proxy is `codex_stdio_to_uds::run`, which copies bytes both ways
    (`stdio-to-uds/src/lib.rs:12-46`).
  - The control socket accepts only WebSocket: tungstenite
    `accept_hdr_async_with_config` (`app-server-transport/src/transport/unix_socket.rs:183-243`).
    Path `/daemon/shutdown` on a managed daemon starts shutdown (`:197-204`).
  - A client must therefore send `GET /rpc` with an Upgrade request, then
    masked text frames, each holding one JSON-RPC object without a
    `"jsonrpc"` field.
  - **Verified:** a plain JSON line through the proxy made the server log
    `failed to upgrade control socket websocket connection: … httparse error:
    invalid token`. The proxy exited **0** with empty stdout. A failure is
    therefore indistinguishable from an empty result unless the client checks
    for the 101 handshake.
  - Only `--listen stdio://` speaks newline-delimited JSON. That starts a new
    app-server, not a client of the daemon.
- **Handshake:**
  - `{"id":0,"method":"initialize","params":{"clientInfo":{"name":…,"version":…},"capabilities":{"experimentalApi":false}}}`.
  - Requests before it are refused with "Not initialized" (`message_processor.rs:1009-1011`).
  - Experimental methods need `experimentalApi: true` (`:1013-1016`).
  - The `initialized` notification is only logged (`:768-772`).
- **Auto-start:** none. The proxy only connects.
  - **Verified:** `proxy --sock /nonexistent` printed "failed to connect to
    socket … No such file or directory", exited 1 in 30 ms, and created no
    process or socket.
  - What starts a daemon is the TUI's `daemon_auto_start`; see the prior doc.
- **Other sockets:**
  - The proxy takes `--sock PATH`, and a direct client connects to that path.
  - A server listens with `codex app-server --listen unix://PATH`; plain
    `unix://` means the default path.
  - A TUI connects with `codex --remote unix://PATH`
    (`tui/src/lib.rs:477-488`).
- **Latency (verified):** `thread/read` measured 8 times each on an idle local
  server:

| Path | connect + WS + `initialize` | request | protocol total | wall clock incl. Python start |
|---|---|---|---|---|
| Direct AF_UNIX | 0.7–0.9 ms | 2.1–2.4 ms | 2.8–3.4 ms | 19–21 ms |
| Via `codex app-server proxy` | 28–31 ms | 2.1–2.3 ms | 33–37 ms | 51–55 ms |

- **Go stdlib:** a direct Go client needs a minimal WebSocket client
  (handshake, masked frames, ping/pong): about 150 lines with no dependency.
  The proxy saves only the default-path lookup, not the framing.

## C5. Codex hooks in 0.166

### `PermissionRequest` decisions

- **Order:** approval precedence is hooks first, then Guardian or the user
  (`core/src/tools/approvals.rs:526-548`).
  - `run_permission_request_hooks(...).await` returns Allow (→ Approved), Deny
    (→ Denied with message), or None (→ `request_reviewer_approval`, which
    prompts the client).
  - So the hook is awaited before any client sees anything.
- **Output schema** (`hooks/src/engine/output_parser.rs:184-205`):
  `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"|"deny","message":"…"}}}`.
  - A deny without a message uses "PermissionRequest hook denied approval"
    (`:416-428`).
  - `updatedInput`, `updatedPermissions`, `interrupt: true`, `continue:
    false`, `stopReason` and `suppressOutput` mark the hook Failed, and its
    decision is dropped (`:381-391,401-414`).
  - Several hooks: any deny wins, otherwise any allow
    (`hooks/src/events/permission_request.rs:156-173`).
  - Exit code 2 with stderr means deny. Exit 0 with empty or non-JSON stdout
    means no decision. Malformed JSON, other exit codes and timeouts mark the
    hook Failed, with no decision (`:201-288`).
  - Async hooks cannot decide (`hooks/src/engine/mod.rs:207`).
- **Timeout:** handler key `timeout`, in seconds. The default is 600 and the
  minimum 1; `Interrupt` and `SessionEnd` default to 1 and are capped at 3
  (`hooks/src/engine/discovery.rs:950-970`). On timeout the normal approval
  prompt follows.
- **Verified, allow:** the hook slept 4 s, then returned `allow`. The command
  ran, no client received `requestApproval`, and the TUI showed no dialog.
- **Verified, deny:** the hook slept 6 s, then returned `deny`.
  - 3 s into the hook the TUI showed "• Working (5s • esc to interrupt) ·
    Running hook", with no dialog.
  - Afterwards it showed "• Blocked by hook └ denied by tmag-research probe",
    and the model reported the refusal.
  - `thread/status/changed` stayed `active` with `activeFlags: []`, never

### Payload facts

- **`transcript_path`:** every event's payload has the key, as a nullable
  string (`hooks/src/schema.rs:43-66`).
  - It comes from `sess.hook_transcript_path()`. That is `None` for ephemeral
    threads and non-local thread stores (`core/src/session/session.rs:1085-1086`;
    `thread-store/src/live_thread.rs:400-411`), and otherwise forces the
    rollout file to exist (`core/src/session/mod.rs:5600-5619`). The
    daemon/embedded choice plays no part.
  - **Verified in both modes.** Daemon-style (private server):
    `…/sessions/2026/11/03/rollout-2026-11-03T13-15-31-<thread>.jsonl` on
    SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest,
    PostToolUse, Stop and Interrupt. `--no-daemon`: the same layout, with hooks
    descending from the TUI (`codex` → `zsh` → `tmux: server`).
- **`turn_id`:** **verified** equal to the id `turn/start` returned, and to
  the rollout's turn ids (C6).
- **`Interrupt`:**
  - Payload: `session_id, turn_id, transcript_path, cwd, hook_event_name,
    model, permission_mode` (`hooks/src/schema.rs:628-639`).
  - It fires only when the turn aborts with `TurnAbortReason::Interrupted`
    (`core/src/tasks/mod.rs:858-859`), never for subagents
    (`core/src/hook_runtime.rs:504-506`). Other abort reasons do not fire it.
  - **Verified:** Esc in the TUI during an escalated `sleep 30` fired
    `Interrupt` with the turn's `turn_id`. No `Stop` fired, and
    `turn/completed` had `status: interrupted`. `turn/interrupt` from a
    client is the same code path.
  - The escalated command kept running as a background terminal after the
    interrupt: the TUI showed "1 background terminal running · /ps to view ·
    /stop to close". `PostToolUse` for it arrives only when it ends, outside
    the turn.

## C6. Transcript (rollout)

- **Path:** `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-YYYY-MM-DDTHH-MM-SS-<thread id>.jsonl`,
  in local time (`rollout/src/recorder.rs:1775-1791`). After a revert it
  becomes `…_<rollout id>.jsonl` (`rollout/src/rollout_file_name.rs:70`).
- **Format:** JSONL `{timestamp (UTC ms), ordinal?, type, payload}`.
  - Types: `session_meta`, `response_item`, `event_msg`, `turn_context`,
    `token_usage_record`, `world_state`, `compacted`, `inter_agent_*`,
    `retained_context`, `security_risk_score`, `dynamic_tools_updated`,
    `realtime_item` (`history/src/rollout_payload.rs:31-75`).
  - **Verified** on a test thread: `event_msg, response_item, session_meta,
    token_usage_record, turn_context, world_state`. `session_meta` is large:
    ~130 KB after one trivial turn.
- **Turn ids:** **verified** on all 5 turns of a test thread. Every hook
  `turn_id` appears in `event_msg:task_started`, `turn_context`,
  `event_msg:item_completed`, `event_msg:task_complete` (or
  `event_msg:turn_aborted` for the interrupted turn) and `token_usage_record`.
  `response_item` lines carry no turn id; attribute them by position after
  `task_started`/`turn_context`.
- **Write cadence:** each persisted event is recorded and then flushed
  (`thread-store/src/local/live_writer.rs:459-467`; `rollout/src/recorder.rs:2008-2010`).
  - The policy drops deltas, hook events, approval requests, exec begin/end
    and `item_started` (`rollout/src/policy.rs:128-227`).
  - **Verified:** line timestamps follow events inside a turn. For example, a
    tool output was written at the moment its approval was answered, 10 s
    before `task_complete`.
  - **Verified:** before the first turn the file does not exist, though
    `thread/read` already returns `path`.
- **Compression:** `.jsonl.zst` exists only for files untouched for at least
  7 days, and only when the off-by-default feature or `rollout/compress` is
  used. Resume restores plain JSONL (`rollout/src/compression.rs:114-125,371`).
- **`thread/read`:** returns `thread.path` (`v2/thread_data.rs:262-263`,
  "[UNSTABLE] Path to the thread on disk"). It is `null` for ephemeral threads
  (verified on the title-helper thread).

## C7. Pane input

### Reachability of `--no-daemon`

- Listener acceptors exist only in the standalone app-server
  (`app-server/src/lib.rs:831-859`). The embedded server is in-process
  channels (`app-server-client/src/lib.rs:5-21`), with
  `remote_control_handle: None` (`app-server/src/in_process.rs:533`).
- **Verified:** the `--no-daemon` TUI process held 4 connected `u_str`
  sockets and no listening Unix or TCP socket (`ss -xlpn`, `ss -tulpn`).
- The pane is therefore its only input channel.

### Composer behaviour

All of this was verified in a 0.166 TUI inside tmux, unless marked.

| Situation | Behaviour | Evidence |
|---|---|---|
| Draft typed, then `paste-buffer -p` + `send-keys Enter` | **Concatenated.** "draft-text " + paste was submitted as `draft-text Reply with exactly: pasted-ok`. A paste is inserted at the cursor (`tui/src/bottom_pane/chat_composer/paste_input.rs:70-74,200`). A real bracketed paste resets the paste-burst heuristic, so the following Enter submits (`paste_burst.rs:462-469`). | Live |
| Large paste | Over 1000 chars it becomes `[Pasted Content N chars]` and is expanded on submit. A leading `/name` runs a slash command; a leading `!` runs a local shell command. | Source (`chat_composer.rs:466,3281-3311`; `chatwidget/input_submission.rs:256-259`) |
| Ctrl+C, non-empty composer | **Clears the whole draft** (multi-line included) and saves it to local history; no other effect. | Live; `bottom_pane/mod.rs:1052-1064` |
| Ctrl+C, empty composer | Interrupts a running turn; **quits when idle**; cancels an open modal. | Source (`chatwidget/interaction.rs:624-635`) |
| Esc, turn running | **Interrupts**, even with a draft; the draft stays. | Live; `bottom_pane/mod.rs:1826-1841` |
| Esc, idle | Kept the draft (non-empty composer). On an empty composer, Esc primes **rewind/backtrack**: a second Esc opens a preview, then Enter rewinds. | Live; `app/input.rs:642-681` |
| Approval dialog open, paste + Enter | **Paste dropped, Enter approves** ("✔ You approved codex to run touch h.txt"). Keys: y approve, a session, p prefix, d decline, Esc/n cancel (abort). | Live; `approval_overlay.rs:601-608,848`; `bottom_pane_view.rs:157` |
| Enter while a turn runs | Submits as `turn/steer` to the active turn; Tab queues. | Source (`app/user_turn_submission.rs:31-44`) |
| `@` or slash popup open | Enter selects the item, not submit. | Source (`chat_composer.rs:2207-2228`; `slash_input.rs:375-414`) |
| Viewing a subagent | "Direct input is disabled"; Enter keeps the draft. | Source (`chat_composer.rs:3344-3363`) |

- **Interrupt key:** Esc (binding `interrupt_turn`) whenever a turn runs and no
  popup or modal is open. Ctrl+C only on an empty composer. The TUI sends
  `turn/interrupt {threadId, turnId}` (`app/thread_routing.rs:692-720`).
- **Clearing the composer:** no single key is always side-effect free.
  - Ctrl+C is safe only when the composer is known to be non-empty and no
    modal is open; otherwise it may interrupt or quit.
  - Ctrl+U only clears to line start, so a multi-line draft needs repeats.
  - Avoid Esc (interrupt or rewind), Ctrl+D (quit when empty), Ctrl+T, Ctrl+R,
    `?`, Ctrl+G, Shift+Tab and Shift+Left/Alt+Up (pulls a queued message back).
  - Keys are configurable through `tui.keymap.<context>.<action>`
    (`keymap.rs:816-876`), so a user may have remapped any of them.
- **Delayed approval prompt:** a new approval prompt is held back until 1 s
  after the last composer activity, and a paste counts as activity
  (`bottom_pane/mod.rs:243,794-809`). This protects paste+Enter only if Enter
  arrives before the prompt is shown. **Verified** that once the prompt is
  shown, paste+Enter approves.

## C8. Stability

- **Stable** (present in `generate-json-schema` without `--experimental`):
  - `initialize`, `thread/start`, `thread/resume`, `thread/read`,
    `thread/turns/list`, `thread/items/list`, `thread/loaded/list`,
    `thread/list`, `thread/unsubscribe`, `thread/inject_items`, `hooks/list`,
    `turn/start`, `turn/steer`, `turn/interrupt`;
  - server requests `item/commandExecution/requestApproval`,
    `item/fileChange/requestApproval`, `item/permissions/requestApproval`,
    `item/tool/requestUserInput`;
  - notifications `serverRequest/resolved`, `thread/status/changed` (flags
    `waitingOnApproval`, `waitingOnUserInput`), `thread/started`,
    `thread/closed`, `turn/started`, `turn/completed`, `item/started`,
    `item/completed`.
  - `item/tool/requestUserInput` is in the stable schema although its doc
    comment says "EXPERIMENTAL" (`common.rs:1860`).
- **Experimental** (`#[experimental]`, needs `capabilities.experimentalApi`):
  - methods: `thread/items/read`, `thread/queue/*`, `thread/search`,
    `thread/readState/*`, `turn/settings/update`, `thread/backgroundTerminals/*`
    (`common.rs:573-1139`);
  - `turn/start` fields `environments`, `runtimeWorkspaceRoots`,
    `additionalContext`, `responsesapiClientMetadata*`, and `approvalPolicy`
    (nested variants) (`v2/turn.rs:211-242`);
  - `thread/start` fields such as `permissions`, `historyMode` and
    `dynamicTools`.
- **Unstable by annotation:** `Thread.path`.
- **Project-level caveats:** the generated schemas are "specific to the Codex
  version you ran". The daemon is "experimental and its lifecycle contract may
  change" (`app-server-daemon/README.md:3-4`). The docs call WebSocket
  transport experimental, and that is the only transport the daemon socket
  offers.
- **Hooks:** the hook input and output schemas are checked in under
  `hooks/schema/generated/` and documented, so they are the more stable
  surface.

## Implications for channel choice (inferred)

| Verb | Daemon thread | `--no-daemon` thread |
|---|---|---|
| `answer` | Protocol: join, take the replayed request, answer, wait for `serverRequest/resolved`, disconnect. Pane keys would also work (y/d/Esc), but blindly. | Pane only. The dialog's keys are the only path, and Enter approves. |
| `interrupt` | Protocol `turn/interrupt` with the hook-reported `turn_id`; it needs no join. Use a timeout, because of the anomaly above. | Pane: Esc. It interrupts even with a draft, but primes rewind when idle, so send it only when the session is working. |
| `send` | Protocol `turn/start` would bypass the composer and the approval-dialog hazard. But it steers if busy, and it marks tmag as the thread's client. The pane works too, but concatenates a draft, and Enter approves an open dialog. | Pane only, with the hazards above. |
| `transcript_path` | Hook payload (already received), or `thread/read.path`. | Hook payload. |

## Lessons for future experiments

- **A request-level `hooks` key replaces the whole `hooks` table.** Passing
  `config: {"hooks": {…}}` to `thread/start` dropped the `hooks.state`
  disables given on the server command line, so the user's own hooks ran
  once for that test thread. Define probe hooks only on the server command
  line, together with the disables, and confirm with `hooks/list`.
  `bypass_hook_trust` alone still respects `enabled`
  (`hooks/src/engine/discovery.rs:917-925`).
- **A private `TMAG_STATE_DIR` does not isolate tmux.** The tmag plugin hook
  that ran in the test thread used a scratch state directory but reconciled
  panes on the user's default tmux server. Finding an attachment its own
  state did not know, it cleared it; the user's tmag attached the pane again
  (three `Attach` events). Two state directories on one tmux server undo each
  other's attachments. Experiments must point `TMUX_TMPDIR` at a private
  directory as well, as AGENTS.md says.
