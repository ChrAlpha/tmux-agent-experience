# v0.1 Feasibility Assessment

Date: 2026-11-03. Inputs: prior desk research (Nowledge Mem thread
`ext-openai-nhpsrsx`), Codex source at tag `rust-v0.166.0`, and hands-on
experiments on an isolated tmux server (`tmux -L axlab`).

Environment under test: tmux 3.3a (Debian), Claude Code 2.1.316,
codex-cli 0.166.0, Linux (WSL2 + Dev Container).

## Verdict

v0.1 is feasible as a pure tmux plugin with no resident server, provided that:

1. Codex pane identity is resolved from evidence the hook gathers itself
   (pane title + cwd), never from `$TMUX_PANE`.
2. The remote client (SwiftUI) is moved out of v0.1; v0.1 ships the contract it
   will consume instead.
3. Events are persisted as an append-only log, which makes a daemon unnecessary
   even for resumable remote watching.

## Decisions

- **Name**: `tmag` (tmux + agent). Registries checked 2026-11-03: free on
  Homebrew, npm, crates.io and Debian, with no tmux-related GitHub project.
  `tmax` was rejected: `theo-kirby/tmax` is an active tmux plugin that already
  shows Claude/Codex agent activity.
- **Language**: Go. One static binary, `tmag`, serves the hook hot path and the
  query CLI. A future resident mode is a subcommand (`tmag serve`), not a second
  binary; `tmagd` is reserved as its process / service-unit name.
- **Minimal footprint**: the project never edits user or agent configuration
  files. Every piece is installed and removed by the host's own mechanism.
- **Privacy**: prompt text and assistant output are never persisted.

## Verified facts

### tmux (3.3a, baseline ≥ 3.2)

| Primitive | Result |
| --- | --- |
| Pane user options (`set -p @tmag_*`) from an external process | Works. Usable as the live registry. |
| Control mode `refresh-client -B` subscription | Works, but **lossy**: rapid `a..e` coalesced to `e`; an intermediate value inside one second was dropped. State channel only, never an event log. |
| OSC 0 title → `#{pane_title}` | Works. Shell prompts (e.g. zsh themes) overwrite the title once the agent exits, so the title is only meaningful while the agent is foreground. |
| OSC 7501 (agent state sequence) | Swallowed by tmux; not observable without `pipe-pane`. |
| tmux 3.8 (2026-09-09) monitors, `set-hook -B`, `wait-for -E`, OSC 133 events | Exists upstream. Optional acceleration only; distros ship far older versions. |

### Claude Code (2.1.316)

- Hooks are children of the agent process: `$TMUX_PANE` and `$TMUX` are correct.
- `UserPromptSubmit` and `Stop` share `prompt_id`, a usable turn id.
- **Queued prompts break turn correlation**: a prompt submitted while busy fires
  `UserPromptSubmit` carrying the *running* turn's `prompt_id`; its own `Stop`
  carries an id never announced before.
- `Stop` is not "idle": payload includes `background_tasks` and `session_crons`.
- Delivery: `send-keys -l <text>` + `Enter`, and `paste-buffer -p` (bracketed,
  multi-line) + `Enter`, both submitted reliably.
- The workspace-trust dialog appears before `SessionStart`: an agent can be
  waiting on the user with zero hooks fired.
- Hooks can ship inside a Claude Code plugin (`claude plugin`).

### Codex CLI (0.166.0)

- `daemon_auto_start` is stable and on by default. The TUI is a client of a
  shared managed app-server daemon, and **hooks are spawned by the daemon**.
- Hook env is the daemon's launch-time env (`hooks/src/registry.rs:83`); the
  daemon README states per-client env isolation is not provided. Observed
  locally: daemon env has no `TMUX*` at all. If the daemon is first started
  from a pane, every hook sees *that* pane's `TMUX_PANE` — plausible and wrong.
- Hook payloads carry `session_id`, `turn_id`, `cwd`, `agent_id` (subagents),
  and a `permission-request` event, but nothing identifying the client, pid or
  tty. Neither the app-server protocol nor `state_5.sqlite` maps threads to
  clients.
- Default terminal title is activity, thread-name, project-name. Thread names
  resolve to ids through `~/.codex/session_index.jsonl` (`{id, thread_name,
  updated_at}`); locally 626/626 entries are named, 13 names are duplicated.
  Before a thread starts the title is just `codex`.
- `[tui] terminal_title` can include `thread-id` (29-char UUID prefix + `...`)
  and `run-state` (Working / Waiting / `[ ! ] Action Required`). This requires a
  user config change, so it is an optional precision upgrade, not a dependency.
- `codex --no-daemon` or `features.daemon_auto_start = false` restores env
  inheritance, at the cost of the command center, shared threads and remote
  control. Most `-c` overrides also silently force in-process mode.
- Codex shows a folder-trust dialog before any thread exists.
- Hooks can ship inside a Codex plugin; Codex asks the user to trust plugin
  hooks once (`hooks.state` in `config.toml`).

### Corrections to the prior desk research

- `woonyong-choi/tmux-agents` does not exist; the A2A-over-MCP precedent it
  cited is unverified.
- The shared-daemon identity problem is the **default path**, not an edge case.
  `tmux-agent-panel` documents exactly the wrong assumption ("hooks run as
  children of the agent process, so `$TMUX_PANE` identifies the right pane").
- "Without a daemon there is no event history" is not true: an append-only log
  written by hooks gives lossless, resumable events with no resident process.
- Both vendors now ship first-party remote control (`claude remote-control`
  with the Claude mobile app; `codex remote-control pair`). Structured chat and
  approvals on a phone are already covered per vendor; the project's remote
  value is a cross-agent inbox and A2A, not another chat surface.

## Design consequences

1. **Identity is evidence-based, per adapter.**
   - Claude: `$TMUX_PANE` + `session_id`.
   - Codex: hooks detect daemon mode (ancestor process is
     `codex app-server … --managed-daemon`) and then ignore `$TMUX_PANE`. At
     hook time the TUI is foreground, so the hook queries tmux directly: panes
     running `codex` whose title resolves to the hook's `session_id` (thread id
     prefix if configured, otherwise thread name via `session_index.jsonl`),
     cross-checked against the hook `cwd`. No tmux hooks are needed.
   - Insufficient or ambiguous evidence ⇒ `unbound`. Control operations
     refuse `unbound`.
2. **Two channels, never conflated.**
   - Live state: pane options (`@tmag_state`, `@tmag_agent`, `@tmag_session`, …),
     subscribable via control mode; they vanish with the pane.
   - Events: per-server append-only JSONL under
     `$XDG_STATE_HOME/tmag/` with a monotonic `seq` (flock),
     so `tmag watch --since <seq>` resumes after disconnects. Records hold ids,
     states and timestamps only. Size-bounded rotation.
3. **State model is honest.** `starting | working | blocked | idle | unknown`,
   plus `unbound`. Pre-session dialogs and unhooked agents are `unknown`, never
   `idle`. `Stop` with background tasks is not `idle`.
4. **`tmag send` is gated**: target bound, identity re-checked immediately before
   delivery, state `idle`. Otherwise refuse (no mailbox in v0.1). This is also
   what keeps `prompt_id` / `turn_id` correlation valid for `tmag wait`.
5. **Fail-open hooks**: always exit 0, bounded runtime, no network. A broken or
   missing binary must never block an agent turn.
6. **Version-pinned adapters.** Codex title format, hook schemas and the daemon
   are explicitly unstable; `tmag doctor` checks agent versions against tested
   ranges.

## Packaging (install = uninstall in reverse)

| Piece | Installed by | Removed by | Footprint |
| --- | --- | --- | --- |
| `tmag` binary | release download / `go install` | delete file | one file |
| Claude Code integration | `claude plugin install` | `claude plugin uninstall` | plugin dir |
| Codex integration | Codex plugin install + one-time hook trust | Codex plugin removal | plugin dir |
| tmux plugin (TPM) | `set -g @plugin …` | remove the line | optional status-line formats and key bindings only |
| Runtime state | written on use | `rm -r $XDG_STATE_HOME/tmag` | event log |

`tmag doctor` reports exactly what is installed; `tmag uninstall --dry-run` prints
the removal steps. Removing any piece leaves running tmux sessions and agents
untouched.

## Revised v0.1 scope

1. **Awareness**: Claude Code and Codex, identity + state, daemon-aware Codex
   binding, explicit `unbound` / `unknown`.
2. **Contract**: versioned JSON for `tmag list | inspect | watch | read | send |
   wait | doctor`; resumable event log; gated delivery.
3. **Removability**: everything installed and removed through native host
   mechanisms; no edits to `tmux.conf`, agent settings or hook files beyond what
   the user adds.

Out of v0.1: resident daemon, SwiftUI client (separate project consuming
`tmag watch --json` over SSH), mailbox, screen parsing, tmux 3.8 monitors,
worktrees, orchestration, session restore.

## Open spikes

- Codex thread-name timing (when a new thread gets its name), thread switch,
  `/new`, subagent view, title truncation, and title clobbering by other
  programs.
- Claude `PermissionRequest` / `Notification` / `AskUserQuestion` coverage for
  `blocked`.
- Codex plugin packaging of hooks and the trust flow on first install.
- macOS process-ancestry detection for daemon mode.

## Landscape

Crowded, young and small: `tmux-agent-panel` (Go, ★1), `tmux-agent-status`
(Shell, ★291), `tmux-agent-wizard` (Rust, ★18, screen parsing with a watcher per
pane), `muxa` (Rust, ★43, own daemon and entry point), `workmux` (★2987,
worktree-centric). None combines a native tmux entry, correct Codex daemon
binding, a versioned machine contract and a lossless resumable event log. That
combination is the differentiation, and it is narrow: it holds only if the
contract is treated as the product.
