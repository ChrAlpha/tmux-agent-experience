tmux-agent-experience · tmag

A tmux plugin that knows what your coding agents are doing.

Claude Code, Codex, Pi and oh-my-pi in your usual panes. See who needs you, jump there, and let agents hand work to each other.

Install in one prompt GitHub

From install to first handoff

About ten minutes with tmux 3.2+ on Linux or macOS, TPM and curl. Every step is safe to repeat, and the same steps update tmag later.

  1. Install the plugin

    Paste this into the coding agent you run in tmux. It asks before it edits your tmux configuration, connects the agent it runs in, and checks the result.

    Read https://raw.githubusercontent.com/ChrAlpha/tmux-agent-experience/main/SKILL.md and follow it to install or update tmag for the AI tool I am using.

    By hand: add the plugin above TPM's run line and press prefix I. The plugin downloads the released tmag binary for its version, checks its SHA-256 and keeps it in its own directory.

    set -g @plugin 'ChrAlpha/tmux-agent-experience'

  2. Connect your agents

    Press prefix M-a. A popup shows the commands that install tmag's plugins through each agent's own plugin manager, runs them once you confirm, then runs tmag doctor.

  3. Start fresh sessions

    Hooks load when a session starts, so start new agent sessions in tmux panes. In Codex, approve tmag's hooks with /hooks and run /title once to turn on thread-id; Codex panes attach after the first prompt.

  4. Check, then hand off

    tmag doctor without ✗ lines means you are done. Press prefix a to see your agents, then ask one to bring in another:

    Ask the Codex agent in ~/src/web to review my last commit, and wait for its answer.

    Your agent runs tmag send --wait, then tmag read --last. Codex reads who asked on the first line, which tmag writes:

    [tmag] From claude 1787a44e-…, another agent. Answer in your final message.

Best practices

Habits that make tmag pay off once several agents run at once.

Notice what needs you

01 Put state where you already look

The status line counts agents by state and pane borders name each one, so a glance replaces visiting panes. Keep your own status-right and add #{tmag_status} anywhere in it.

Set options above TPM's run line: the plugin reads them when it loads.

# "1 blocked · 1 working · 1 idle" in the status line
set -g status-right '#{tmag_status} | %H:%M'
set -g status-right-length 60

# "claude blocked permission" on each agent's pane border
set -g pane-border-status top
set -g pane-border-format ' #{pane_index} #{?#{E:@tmag-pane-status},#{E:@tmag-pane-status},#{pane_current_command}} '

set -g @plugin 'ChrAlpha/tmux-agent-experience'
run '~/.tmux/plugins/tpm/tpm'

02 Let alerts come to you

An agent that blocks or finishes in a pane you are not looking at rings its window's bell. prefix A takes you to the agent waiting longest, blocked ones first; tmux's prefix M-n and M-p visit flagged windows.

Away from the terminal, @tmag-notify runs your own command with the alert in TMAG_* variables, unless you typed on a server showing that agent in the last minute. tmag notify sends a test alert.

# Linux desktop
set -g @tmag-notify 'notify-send "$TMAG_TITLE" "$TMAG_MESSAGE"'

# macOS
set -g @tmag-notify 'osascript -e "on run argv" -e "display notification (item 2 of argv) with title (item 1 of argv)" -e "end run" "$TMAG_TITLE" "$TMAG_MESSAGE"'

Work with several agents

03 One agent per pane, one worktree per task

Parallel tasks in separate git worktrees never trip over each other. Agents that do share a repository check their peers through tmag before they switch branches, rewrite history or stop processes, and leave a peer's changes alone.

git worktree add -b fix/login ../web-login
tmux new-window -n login -c "$(realpath ../web-login)"

04 Ask in plain words

You never type tmag's verbs to delegate. Ask your agent; the tmag-peers skill picks the verb, and tmag delivers through the other agent's own channel. A working agent reads a message at its next step; Claude Code may hold one for its person's approval.

tmag writes the first line from the sender it proves. A person's prompt gets none, and an agent never acts on its own session.

You asktmag runs
“Ask the Codex agent to review this diff and wait for its answer.”send --wait, then read --last
“Have another agent look into the flaky test and send you what it finds.”send --reply; the peer answers with tmag reply
“Tell the Pi agent that the API schema changed.”send

What the other agent reads first, row by row:

[tmag] From claude 1787a44e-…, another agent. Answer in your final message.
[tmag] From claude 1787a44e-…, another agent. When done, send your answer on stdin to: tmag reply 1787a44e-… -
[tmag] From claude 1787a44e-…, another agent. No answer needed.

05 Keep approvals yours

With @tmag-answer at its default, on, you can decide a Claude Code or Codex permission prompt from any pane or script while the agent's own dialog stays open. An agent that tries is refused, so agents never approve each other by accident.

Set it to agents only if you want them to, or off to decide in the agent alone.

$ tmag inspect 1787
…
request: 3fdce4c70dfa (permission, Bash)
…
$ tmag request 1787 3fdce4c70dfa
1787a44e permission asks: Bash
{
  "command": "go test ./..."
}
$ tmag answer 1787 3fdce4c70dfa allow
answered 1787a44e (hook) seq 1794457203091588

Build on it

06 Script against JSON, not screens

Put the plugin's bin/ on your PATH. --json follows the versioned tmag/v2 contract; tmag watch prints a snapshot, then one line per change, numbered without gaps so a follower knows what it missed.

export PATH="$HOME/.tmux/plugins/tmux-agent-experience/bin:$PATH"

tmag list --json | jq -r '.sessions[] | select(.state == "blocked") | .id'
tmag wait 01a1 --for idle --timeout 30m && tmag read 01a1 --last
tmag watch

07 Reach agents from elsewhere, on your terms

To reach agents from elsewhere, use the remote companion, tmag-client. On one machine, the hub, tmag-client serve runs in a tmux window and follows the machines it is given; closing the window stops it. Each device pairs with its own single-use invitation, and any one is revoked later. A tunnel of your choice, --tailscale or --access, reaches it from elsewhere, and push needs one. On iOS, add the page to the home screen before pairing and pair from there: the home-screen app keeps its own storage, so pairing done in Safari does not carry over, and it is the app that receives notifications.

The client comes from its own releases, installed as the wiki's Installation & Updates page shows. prefix M-r still opens tmag serve in a tmux window, for integrations and machines no command reaches.

# on the hub: a tmux window that follows another machine
tmag-client serve --machine box='ssh box tmag' \
  --tailscale hub.example.ts.net --owner me@example.com

# each device pairs once; revoke one later
tmag-client auth pair phone
tmag-client auth list
tmag-client auth revoke ID

08 Update with two keys

prefix U updates the plugin through TPM, and prefix M-a brings each agent's plugins to the same version. Codex approves hooks per plugin version: approve tmag's again with /hooks in a new Codex session. Pi's and oh-my-pi's packages update with the plugin.

prefix + U      update the plugin; it fetches the matching binary
prefix + M-a    update tmag's plugins in every agent
/hooks          in a new Codex session: approve tmag's hooks

What tmag leaves alone

  • Your agents. No daemon and no wrapper: agents run as you start them, and tmag serve runs only in a window you open.
  • Your turns. Hooks fail open. A missing or broken tmag never blocks a turn.
  • Your words. Records hold ids, states, paths and times. A reply is read from the agent's own transcript when asked, and kept nowhere.
  • Guesswork. A pane shows a session only when the process table, or Codex's thread-id title, proves it. Anything else is unknown.
  • Your configuration. Agent plugins install through each agent's own plugin manager; tmag never edits their settings.
  • Your choices. Every default has an off switch: @tmag-alert off, a key option set to off, or @tmag-peers off then prefix M-a to keep tmag out of the agents' context.
